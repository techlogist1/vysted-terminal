# Data Battery Diff — BSE 509470 (Bombay Oxygen Investments Ltd)

Fresh-context audit. App trace: `inapp/509470.json` (resolver + fundamentals + quote + full
copilot research invocation, incl. every tool call and the final narrated answer). Reference:
`reference-packs/509470.json` (independent web pack, 11 sources, compiled 2026-07-10, last
close used 2026-07-09).

## Headline finding before the figures

The app's **raw data endpoints** (`/fundamentals/BOMOXY-B1.BO`, `/quotes/BOMOXY-B1`) correctly
resolve and fetch data for **Bombay Oxygen Investments Ltd**, and those figures largely agree
with the reference pack (see table).

But the **copilot's actual final answer to the user** — the last `publish_brief` call in the
same invocation, the one whose markdown/narration the agent spoke aloud — is entirely about
**"Meghmani Organics ($MOL)"**, a completely different, unrelated NSE-listed company. The
narration text (1,227 chars, fully captured) never mentions Bombay Oxygen, BOMOXY-B1, or 509470
once. Every one of the run's own *intermediate* tool calls (`corporate_announcements`,
`price_data`, `shareholding_pattern`, `fundamentals`, `open_company_overview`, `screener_run`)
correctly used `symbol=BOMOXY-B1` — only the final published brief object is wrong, and its
`execution.started_at`/`finished_at` timestamps **precede** this invocation's own research call
by ~52 seconds, consistent with a stale/cross-contaminated brief object leaking in from an
unrelated prior request rather than being freshly generated. The Meghmani figures themselves
are not fabricated (cited to real MOL sources) — they are simply the answer to a different
question the user never asked.

This is the dominant defect in this run and is called out as its own row below; the rest of
the table audits the correctly-scoped fundamentals/quote data against the reference pack.

## Verdict summary

- **11 ok**, **6 watch**, **3 mismatch** (of 20 rows).
- **Identity verdict: MISMATCH.** The underlying data plumbing (resolver, `/fundamentals`,
  `/quotes`) is correctly scoped to Bombay Oxygen Investments and its figures track the
  independent reference pack closely (price, market cap, EPS, 52w high/low, ROE, book value all
  agree within tolerance). But the **actual answer the user received** — the final published
  brief and its narration — is for an unrelated company (Meghmani Organics, $MOL). This is a
  severe, user-facing identity-resolution/synthesis failure, not a rounding or staleness issue.
- Two further internal-consistency bugs (both same-basis, real conflicts, not explainable by a
  disclosed different basis): the research brief's `derived` block nulls out **drawdown-from-52w-high**
  and **52-week-change** even though the run's own successful fundamentals/quote calls for the
  same entity carried the exact inputs (or, for 52w change, the exact output) needed.
- Two genuine **watch**-class basis gaps worth product attention even though they're
  explainable: (a) dividend per share/yield reflect the not-yet-paid Rs 25 declared dividend
  rather than the Rs 35 TTM-paid one — the same staleness pattern the reference pack calls out
  in other aggregators; (b) the fundamentals payload only exposes TTM revenue/profit, not a
  discrete latest-quarter figure, though the TTM values do match the reference's annual FY26
  figures almost exactly.
- No fabricated figures were found — every app-asserted number traces to a real (if sometimes
  mis-scoped or stale-basis) source.

## Non-figure engineering notes (context, not scored above)

- `GET /fundamentals/509470` and `GET /fundamentals/BOMOXY-B1` (bare, no exchange suffix) both
  404 — only the Yahoo-style `BOMOXY-B1.BO` suffix resolves. `GET /quotes/509470` **502s** with
  an internal yfinance-adapter crash (`'PriceHistory' object has no attribute '_dividends'`),
  not a clean 404 — a real bug in the raw-scrip-code quote path.
- The research `tool_use` call's own `input.depth` field says `"quick"` while its `research:begin`
  log line says `depth=normal` — an internal depth-label inconsistency, cosmetic but worth
  fixing since it makes run provenance harder to audit.
- The `filings` sub-call failed because `sec-edgar-mcp` did not bind a port this launch — an
  infra/startup issue, not a data-accuracy issue for this name.
