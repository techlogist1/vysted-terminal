## How to read the app file

The app JSON contains two distinct data paths for this symbol, and they disagree with each other internally — that disagreement is itself the headline finding:

1. **Direct sidecar calls** (`resolved_identity`, `fundamentals.endpoint_used_SIMPLXREA.BO`, `quote`) — these hit the real `/fundamentals` and `/quotes` endpoints with the *correct* Yahoo-style symbol `SIMPLXREA.BO` and got a full, populated response (200 OK).
2. **The AI research-copilot run** (`research_normal`) — internally, the agent's own `resolve_symbol`/`price_data`/`fundamentals` tool calls used a **malformed symbol `SIMPLEXREA.BO`** (typo, extra "E") instead of `SIMPLXREA.BO`. Its `fundamentals` tool call consequently failed (`"yfinance has no instrument data for 'SIMPLXREA'"`), its `derived` metrics (drawdown, 52w change, dividend yield, growth rates) all came back `null`, and the published brief told the user P/E, P/B, market cap, ROE, dividend history, and quarterly results were **all "Unavailable — no provider record."** That claim is false — the sidecar's own correct-symbol endpoint (path 1, captured in the same file) proves the data was retrievable the whole time. On top of that, `publish_confirmation_status` says neither `publish_brief` call was ever confirmed rendered by the terminal.

The metrics table below audits path 1 (the actual data layer) against the reference. The symbol-bug/false-unavailability finding is called out separately since it isn't a numeric discrepancy so much as a reliability defect.

## AI Copilot reliability finding (separate from the figures above)

The `research_normal` trace shows the copilot's own tool-calling loop resolved the symbol correctly at the top level (`SIMPLXREA`) but then called `resolve_symbol`/`price_data`/`fundamentals` with a **typo'd symbol `SIMPLEXREA.BO`** (extra "E") for the actual data pulls. That typo caused:

- Its internal `fundamentals` call to fail outright (`"yfinance has no instrument data for 'SIMPLXREA'"`).
- Every metric in its `derived` block (drawdown-from-high, 52-week change, dividend yield, dividend/share, revenue growth, earnings growth) to come back `null` — even though the app's own correct-symbol `/fundamentals` call (captured two sections earlier in the very same file) had real values for four of those six.
- The **published brief markdown** to assert, in a user-facing "Fundamentals, valuation & dividends — status" table, that P/E, P/B, market cap, revenue/profit/margins, ROE/debt-to-equity, and dividend history were all **"Unavailable — no provider record."** That's a materially false claim given the sidecar demonstrably has this data under the correct symbol.
- `publish_confirmation_status` additionally states neither of the two `publish_brief` calls in this run was ever confirmed rendered by the terminal panel — so it's unclear whether the false-unavailability narrative even reached the user in this instance, but the underlying tool-loop defect (wrong symbol variant reaching `fundamentals`/`price_data`) is real and would reproduce on a future run for this ticker (and likely any ticker where the display symbol needs Yahoo-suffix normalization before being passed to sub-tools).

This is counted as the primary **mismatch** in the structured summary, separate from the `drawdown_from_high` row above (which is one specific symptom of this same root cause).
